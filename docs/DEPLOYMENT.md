## How the app expects to be run

OSC is a standard **Next.js 16 (App Router)** application with:

- a **PostgreSQL 14+** database (that's the only external service it needs),
- **server-rendered pages** (nearly every route is dynamic — it's a
  community site, content changes constantly),
- a **self-bootstrapping database layer** — you never run migrations
  (see [below](#the-zero-ops-database)),
- **no file storage** — images are hot-linked by URL, videos are official
  embeds, so there is no S3/volume to configure,
- an **in-memory rate limiter** — designed for a single instance. If you
  scale to multiple instances, see the note in
  [ARCHITECTURE.md](ARCHITECTURE.md#swapping-the-rate-limiter-for-redis).

The ideal shape is therefore: **one long-running Node process + one Postgres
database**. Serverless (Vercel) also works with caveats noted below.

### Build & start commands

| Purpose | Command |
| --- | --- |
| Install | `npm ci` |
| Build (CI/Docker/hosts) | `npm run build:host` — runs `prisma generate`, regenerates the bootstrap DDL, then `next build` |
| Build (local, DDL already committed) | `npm run build` |
| Start | `npm start` (honors `PORT`, binds `HOSTNAME=0.0.0.0` in the Dockerfile) |

Node **20.9+** is required (`package.json` `engines`); the included Dockerfile
uses Node **22.23.4**, the minimum patched Node 22 release for the
October 26, 2026 Render security advisory. The engine range expresses framework
compatibility, not a security guarantee; production hosts must use a currently
patched, supported Node release.

## Environment variables

| Variable | Required | Purpose |
| --- | --- | --- |
| `DATABASE_URL` | ✅ | Postgres connection string. Use your platform's *internal* URL when the DB and app are in the same network. |
| `AUTH_SECRET` | ✅ | Session signing secret. Generate: `openssl rand -base64 32`. Changing it signs everyone out (harmless otherwise). |
| `ADMIN_PASSWORD` | ✅ (first boot) | Password for the auto-created admin account. Without it, no admin is created and a warning is logged. |
| `ADMIN_USERNAME` | – | Admin username (default `admin`). |
| `AUTH_TRUST_HOST` | ✅ on PaaS | Set `"true"` behind any reverse proxy (Render/Railway/Fly/Vercel all are). Make sure your platform pins the `Host` header to your domain — all major PaaS providers do. |
| `YOUTUBE_API_KEY` | – | Enables `/import` (mass playlist import) and rich YouTube metadata. Everything else works without it. Free at console.cloud.google.com → enable *YouTube Data API v3* → create API key. |
| `PORT` | – | Listen port (default 3000). |
| `NEXT_OUTPUT=standalone` | – | Set at **build** time to produce a self-contained `.next/standalone` server (used by Docker-style deploys). |

## The zero-ops database

**You never run `prisma migrate`.** At boot, `instrumentation.ts` calls
`lib/bootstrap-db.ts → ensureDatabase()`, which:

1. **Creates the entire schema** if the database is empty, from
   `lib/generated/ddl.ts` (a committed snapshot of the Prisma schema as SQL,
   regenerated by `npm run build:host`).
2. **Applies forward-migrations idempotently** for databases created by older
   versions (`ensureExpansionSchema()` — a list of
   `ALTER TABLE … ADD COLUMN IF NOT EXISTS`-style statements).
3. **Creates the admin account** from `ADMIN_USERNAME`/`ADMIN_PASSWORD` if it
   doesn't exist (and re-promotes it to admin if demoted).
4. **Restores from backup** if the catalog is empty and a
   `backups/live-dump.json` file is present (see
   [Backups & restore](#backups--restore)).
5. Kicks off **background backfills** (derived stats, show grouping) without
   blocking startup.

Practical consequences:

- **First deploy**: point the app at an empty database, set the env vars,
  start it. Done.
- **Upgrades**: deploy the new code; schema changes apply themselves at boot.
- **Rollbacks**: old code runs fine against a newer schema (columns are only
  ever added). Rolling back the *database* is never needed for schema reasons.

## Platform guides

### Render

The repo ships a blueprint (`render.yaml`) that provisions a free Postgres and
a free web service in one click.

1. Push the repo to GitHub.
2. In Render: **New + → Blueprint**, select the repo.
3. Render creates `osc-db` (Postgres) and the web service, wires
   `DATABASE_URL` automatically, and generates `AUTH_SECRET`.
4. Set `ADMIN_PASSWORD` in the service's **Environment** tab (the blueprint
   marks it `sync: false`, so it's never in the repo).
5. Optionally set `YOUTUBE_API_KEY`.
6. Deploy. Every subsequent `git push` to the default branch auto-deploys
   (~90–110 s including build).

Free-tier notes:
- The free web service **sleeps after idle** — first request after sleep takes
  ~30–60 s. Paid instances don't sleep.
- Free Postgres has a 1 GB cap and expires after 90 days unless upgraded —
  **schedule backups** (below) if you stay on free.

### Security rebuilds: October 26, 2026 Render advisory

Sources: [Render eMudhra guidance](https://render.com/docs/advisory-emudhra)
and [Node October 21 security releases](https://nodejs.org/en/blog/vulnerability/october-2026-security-releases).

The Dockerfile pins `node:22.23.4-alpine` so a build cannot silently use an
older Node 22 patch. Update the pin as later security fixes ship. The same
image supplies Node for dependency installation, the build, and production.
Node's patched bundled CA store addresses its certificate handling; updating
Alpine's system store alone would not patch Node. The Dockerfile also upgrades
`ca-certificates` from the configured Alpine repositories and regenerates the
system bundle before `npm ci`. This does not prove that the distribution's
available package contains every required fix: verify the resulting image.

Checked-in outbound application clients use `fetch`; no custom CA bundles,
TLS verification bypasses, or PHP runtime were found in this repository.
No advisory-specific npm dependency update was identified. This is not a
claim that all dependencies are free of vulnerabilities. Libraries added later
that bundle certificates or TLS implementations need their own updates.

`render.yaml` describes a Docker web service and Postgres database. It does
**not** establish that a live Render service exists or identify its running
image. A floating base tag in an older deployment does not update a running
container. A restart alone is not a rebuild.

For an existing deployment:

1. Confirm the actual service, linked repository, deployed branch/commit,
   Dockerfile path, and Docker runtime in the Render dashboard. Check every
   service using this image, including any separately configured workers.
2. Merge the patched Dockerfile and rebuild from that commit. Use Render's
   **Manual Deploy → Clear build cache & deploy** so a cached certificate
   installation layer is not reused. For other Docker hosts, use
   `docker build --pull --no-cache -t osc .` and replace the running container.
   A Docker service gets Node from its image; setting Render's native-runtime
   `NODE_VERSION` does not update this Dockerfile.
3. Inspect the built image before deploying, and repeat in the running service:

   ```sh
   node --version
   apk info -v ca-certificates ca-certificates-bundle
   test -s /etc/ssl/certs/ca-certificates.crt
   ```

   Require Node 22.23.4 or a later patched 22.x release for this image. Record
   the image digest, Alpine package versions, deployed commit and deployment ID.
   Review `NODE_OPTIONS`, `NODE_EXTRA_CA_CERTS`, `SSL_CERT_FILE`, `SSL_CERT_DIR`,
   and `NODE_TLS_REJECT_UNAUTHORIZED` in the service's environment. Overrides
   and separately mounted bundles can change trust; update any custom bundle
   and keep verification enabled. Do not print unrelated secrets.
4. From the running container with the app's environment, exercise Node's
   `fetch` (the client used by the checked-in outbound app code):

   ```sh
   node --input-type=module <<'JS'
   const urls = [
     "https://render.com/", // positive control: must connect successfully
     "https://dv-g3b-emudhra.we-have-a-problem.com/",
     "https://dv-g3b-aaa-emudhra.we-have-a-problem.com/",
   ];
   for (const url of urls) {
     try {
       const response = await fetch(url, {
         redirect: "manual", signal: AbortSignal.timeout(10000),
       });
       await response.body?.cancel();
       console.log(url, "CONNECTED", response.status);
       if (url !== urls[0]) process.exitCode = 1;
     } catch (error) {
       console.error(url, error.cause?.code, error.cause?.message ?? error.message);
       // Review each error: DNS failures/timeouts do not prove rejection.
       process.exitCode = 1;
     }
   }
   JS
   ```

   The positive control must connect. Both compromised-certificate endpoints
   must fail specifically with certificate verification errors. Any HTTP
   response, including redirects or errors, means the TLS connection was
   accepted. The snippet deliberately exits nonzero on errors so its exit
   status alone cannot be mistaken for proof of remediation; inspect the
   error codes/messages. DNS failures, timeouts, or unavailable test endpoints
   leave the check inconclusive. Testing with host `curl` alone does not
   validate Node's trust store. If the app later adds a custom dispatcher or
   TLS client, repeat the check through that actual client configuration.
5. Confirm the new deployment is serving traffic, then smoke-test sign-in,
   normal page loads and outbound YouTube/Vimeo metadata or playlist imports.
   Only then record deployment remediation as complete. These instructions
   do not assert that any live service has been inspected or redeployed.

### Railway

1. **New Project → Deploy from GitHub repo.**
2. Add a **PostgreSQL** service to the project; Railway exposes
   `DATABASE_URL` — reference it in the app service's variables
   (`${{Postgres.DATABASE_URL}}`).
3. Set `AUTH_SECRET`, `AUTH_TRUST_HOST=true`, `ADMIN_PASSWORD`.
4. Railway auto-detects Next.js (Nixpacks). To force the DDL regen, set the
   build command to `npm run build:host` and the start command to `npm start`.
   Alternatively let it use the **Dockerfile**, which already does both.

### Fly.io

The Dockerfile works as-is.

```bash
fly launch --no-deploy          # detects the Dockerfile; pick a region
fly postgres create             # or use Supabase/Neon and skip attach
fly postgres attach <pg-app>    # sets DATABASE_URL on the app
fly secrets set AUTH_SECRET=$(openssl rand -base64 32) \
                AUTH_TRUST_HOST=true \
                ADMIN_PASSWORD='choose-something-strong'
fly deploy
```

Keep `min_machines_running = 1` (default in recent fly.toml templates is 0 —
change it) so the in-memory rate limiter and resume-position UX aren't reset
by constant cold starts.

### Vercel + hosted Postgres

Works, with caveats — OSC prefers a long-running server.

1. Create a Postgres database at **Neon**, **Supabase**, or **Vercel
   Postgres**. Use the **pooled** connection string (pgBouncer) as
   `DATABASE_URL` — serverless functions open many short-lived connections.
2. Import the repo into Vercel. Framework preset: Next.js.
   Override the build command to `npm run build:host`.
3. Set env vars: `DATABASE_URL`, `AUTH_SECRET`, `AUTH_TRUST_HOST=true`,
   `ADMIN_PASSWORD`, optionally `YOUTUBE_API_KEY`.

Caveats:
- **Bootstrap runs on cold starts** — it's idempotent and fast once the schema
  exists, but the very first request after deploy does the heavy lift. Hit the
  site once after deploying.
- **Playlist imports** run a transaction that can take tens of seconds for
  100-video playlists — set the function max duration ≥ 120 s (Pro plan), or
  keep imports small on Hobby.
- **Rate limiting** is per-lambda-instance, so limits are effectively looser.
  Fine for small communities; use Redis (see ARCHITECTURE.md) if it matters.

### Docker on any VPS

```bash
docker network create osc
docker run -d --name osc-db --network osc \
  -e POSTGRES_PASSWORD=change-me -e POSTGRES_DB=osc \
  -v osc-pgdata:/var/lib/postgresql/data postgres:16-alpine

docker build --pull -t osc .
docker run -d --name osc-app --network osc -p 80:3000 \
  -e DATABASE_URL=postgresql://postgres:change-me@osc-db:5432/osc \
  -e AUTH_SECRET=$(openssl rand -base64 32) \
  -e AUTH_TRUST_HOST=true \
  -e ADMIN_PASSWORD='choose-something-strong' \
  osc
```

Put Caddy/nginx/Traefik in front for TLS. The container is stateless — all
state is in Postgres, so `docker rm` + re-run is always safe.

### Bare Node on a VPS

```bash
sudo apt install -y postgresql   # or use a managed DB
sudo -u postgres createdb osc
git clone <repo> && cd object-stream-community
npm ci
cp .env.example .env && $EDITOR .env
npm run build:host
npm start                        # keep alive with systemd or pm2
```

Sample systemd unit:

```ini
[Unit]
Description=Object Stream Community
After=network.target postgresql.service

[Service]
WorkingDirectory=/srv/object-stream-community
EnvironmentFile=/srv/object-stream-community/.env
ExecStart=/usr/bin/npm start
Restart=always
User=osc

[Install]
WantedBy=multi-user.target
```

## Backups & restore

Two independent mechanisms:

### 1. Database-level (preferred)

Plain Postgres — use your platform's backup feature or:

```bash
pg_dump "$DATABASE_URL" -Fc -f osc-$(date +%F).dump    # backup
pg_restore -d "$NEW_DATABASE_URL" --clean osc-YYYY-MM-DD.dump
```

### 2. Application-level scrape (works with zero database access)

For hosts where you can't reach Postgres at all, the repo includes a scraper
that extracts the full catalog **through the site's own pages** (signed in as
admin, so hidden content and exact metadata are included):

```bash
BASE_URL=https://your-site.example \
ADMIN_USERNAME=admin ADMIN_PASSWORD=… \
npx tsx scripts/scrape-live-site.ts
# → writes backups/live-dump.json
```

**Restore:** commit or copy `backups/live-dump.json` into the deployed app and
boot it against an **empty** database — the bootstrap detects the empty
catalog and refills it from the dump (videos, shows, playlists, users*,
reviews, wiki pages). *Restored accounts get `mustResetPassword` and reclaim
their account with a new password on next sign-in — password hashes can't be
scraped, by design.

Run the scrape on a schedule (cron, GitHub Action) if your database tier is
ephemeral — e.g. Render's free Postgres expires after 90 days.

## Upgrading

1. `git pull` (or merge the upstream release).
2. Redeploy. Schema changes apply themselves at boot — watch the logs for
   `[bootstrap]` lines.
3. If a release adds a column to an existing table, it ships an idempotent
   ALTER in `ensureExpansionSchema()`, so old databases upgrade in place.

Verify a deploy went live (works on any host):

```bash
# The JS chunk fingerprint changes on every new build:
curl -s https://your-site/signin | grep -oE '/_next/static/chunks/[^"]+\.js' | sort | md5sum
```

## Troubleshooting

| Symptom | Likely cause / fix |
| --- | --- |
| `[bootstrap] ADMIN_PASSWORD not set` in logs | Set `ADMIN_PASSWORD` and restart — no admin account exists yet. |
| Redirect loops or `UntrustedHost` errors | Set `AUTH_TRUST_HOST=true` (you're behind a proxy). |
| Sign-ins randomly invalid after redeploys | `AUTH_SECRET` isn't pinned (e.g. regenerating per deploy). Set it once, keep it. |
| Playlist import says an API key is needed | Set `YOUTUBE_API_KEY`. Single-video submits don't need it. |
| Import of a huge playlist times out | The import transaction allows 120 s. On serverless, raise the function duration limit, or import in halves. |
| First page load after deploy is slow | That's the bootstrap creating/patching schema — one-time per deploy. |
| Search is case-sensitive | You're not on Postgres. The app targets Postgres; `mode: "insensitive"` queries depend on it. |
| Rate-limit messages during testing | Limits are per 5–60 min windows (see `lib/rate-limit.ts` call sites). Restarting the app clears them (in-memory). |
